# Stitch (in-editor)

The right-rail AI chat tab inside the builder — one of SiteWeaver's three canonical agent surfaces (see `replit.md` § Agents; the other two are **External CLI agents** and **Offline-zip agents**).

Right-rail chat panel inside `FileEditorClient`. The user asks Claude to edit any file in the tenant's active version. Edits to the **currently open** file land in the editor buffer (Save commits). Edits to **other tenant files** are committed immediately via the builder API.

For per-tool API and "how to add a tool", see `artifacts/homium/src/features/ai-chat-builder/README.md`. This doc is the maintainer's perspective: the non-obvious bits, the SDK gotchas, and the design choices that won't be self-evident from the code.

## How it works

```
client (AiChatPanel)
  ↓ POST { messages, openFile }
/api/builder/tenants/[tenantId]/ai-chat (route.ts → handleAiChat)
  ↓
server/route-handler.ts
  - requireBuilderTenant
  - read styles.css + list version files (active version)
  - buildSystemPrompt
  - streamText({ model, tools: TOOLS, stopWhen: stepCountIs(8) })
  ↓ result.toUIMessageStreamResponse()
useChat (client)
  - sendAutomaticallyWhen: lastAssistantMessageIsCompleteWithToolCalls
  - onToolCall → CLIENT_HANDLERS[name](input, ctx) → addToolResult(...)
  - askChoice rendered as a card; resolves on user click
```

Five tools, all client-side execution: `editFile`, `replaceInFile`, `createFile`, `readFile`, `askChoice`. The server declares the tools without `execute` — AI SDK forwards the call to the browser, the handler runs there, the result is sent back via `addToolResult` and the SDK auto-resends the conversation.

## Architecture decisions worth knowing

- **Client-side tool execution.** All file ops run in the browser via `onToolCall`, not on the server. This is what lets `replaceInFile`/`editFile` mutate the live editor buffer for the open file (no extra round-trip, no Save dialog) while still hitting the builder API for non-open files. The server has zero knowledge of which file is currently open.
- **No confirmation card.** Save is the guardrail for the open file (the live preview shows the unsaved buffer in the iframe). Versioning is the safety net for direct commits. We deliberately don't gate edits behind "Apply?" prompts.
- **Always-pinned context.** Every request includes the open file (path + buffer) plus a structured tenant map in four parts: **critical files** in priority order (`styles.css`, `_general/styles.base.css`, `config.json`, `header.html`, `footer.html`), **pages** (`pages/*.html`), **supporting files** (`resources/brand.md`, `_context/context.md`), and a **folders legend** (with `pages/news/` carrying the article count). **`styles.css` body is no longer inlined** — the model fetches it via `readFile` when it actually needs the rules (saves 12–24 KB per request). `prepareSendMessagesRequest` re-reads `getOpenFile()` at send time so the buffer is current — never use a stale closure.
- **Static tool registry.** `tools/registry.ts` is one import + one entry per tool. We tried `require.context` and codegen; both were over-engineered for ~5 tools. Manual registry wins until the count grows materially.
- **Tool scope as a per-role array.** Each role in `sites/_platform/user-permissions.json` carries an `agentRestrictions: AgentToolName[]` field. The chat route filters the `TOOLS` registry by that set before calling `streamText`, so withheld tools are literally absent from the model's tool list — no client-side gate, no async load to race against. `system-prompt.ts` appends a per-tool restriction note so the model proposes the operator-facing fallback (e.g. "ask the user to create the file from the file tree") instead of trying anyway. Path-level access (which files the agent may write) is handled by the regular builder file routes via `canWriteFilePath` + the `_general/**`/`_platform/**` storage write locks — `agentRestrictions` is purely about which *tools* the agent has, not which paths.
- **Per-tool result enrichment for context-confused models.** Buffer-mode write tools return `{ ok: true, message: BUFFER_APPLIED_MESSAGE, ... }` from `tools/types.ts`. Without that explicit "Applied. Still needs Save." string, Sonnet sometimes re-reads the post-edit file (which now contains its own change) and concludes "looks like it's already this way." See `BUFFER_APPLIED_MESSAGE` in `tools/types.ts` for the canonical wording — both `editFile` and `replaceInFile` import it.

## Gotchas

These have all bitten us. Don't undo them without reading the comment first.

### 1. `addToolResult` must NOT be awaited inside `onToolCall`

The AI SDK processes stream chunks (including `onToolCall`) inside an internal `SerialJobExecutor`. `addToolResult` itself queues work on that same executor. `await addToolResult(...)` deadlocks the queue — the chat hangs with the toast stuck on "Reading…/Editing…" forever and no follow-up POST is made.

Fix: fire-and-forget, no await. The SDK re-runs `sendAutomaticallyWhen` (`lastAssistantMessageIsCompleteWithToolCalls`) after the stream finishes, which triggers the auto-resend. See the comment in `AiChatPanel.tsx:onToolCall`.

### 2. askChoice must be answered before any other user input

Anthropic's API requires every `tool_use` to be immediately followed by a `tool_result`. If an `askChoice` is unresolved and the user just types a normal message, `sendMessage` posts a fresh user turn — the dangling tool call wedges the entire conversation (every subsequent request 400s).

Fix: `onSubmit` calls `findPendingAskChoice(messages)` first. If a pending askChoice exists, the typed text is routed via `addToolResult({ tool: "askChoice", toolCallId, output: text })` instead of `sendMessage`. This also recovers conversations that are already wedged from prior bugs.

### 3. The "model forgets it just edited" problem

Symptom: model calls `replaceInFile`, gets `{ok: true}`, then in its next turn says *"looks like it already matched."* The system prompt re-pins the file content every turn — and that content is now the post-edit version. The model defaults to treating the pinned content as a "starting state" and doesn't reason "I just changed it, that's why it matches."

Fix: tool result includes `BUFFER_APPLIED_MESSAGE` ("Applied. The file now contains your change in the editor buffer. The user still needs to click Save for this to be permanent."). Don't drop this message — the bytes-changed delta isn't enough signal for Sonnet.

### 4. POST 500 with "Response body should not be disturbed or locked"

Tracked upstream as [vercel/next.js#83453](https://github.com/vercel/next.js/issues/83453) — Next 15 node-runtime middleware intermittently corrupts the request body stream, surfacing as `TypeError: Response body object should not be disturbed or locked` at `fromNodeNextRequest` during NextRequest construction. Hits prod on the auto-resend POST after tool calls — confirmed May 2026 via deployment logs.

**Primary fix**: `api/builder/` is excluded from the middleware matcher in `middleware.ts`. The middleware was contributing nothing on those routes (tenant-by-host rewrite already no-ops for `/api/...`, and every builder route self-gates via `requireBuilderTenant`), so dropping them from the matcher removes the trigger without losing behaviour. Until the upstream bug is patched, anything new under `/api/builder/*` keeps the same self-gating contract.

**Kept as a small safety net**: route-level try/catch in `app/api/builder/tenants/[tenantId]/ai-chat/route.ts` wraps the whole POST, logs the full stack via pino, and returns JSON `{error, message, name}` with status 500 instead of a 50 KB Next default HTML error page. The client renders `error.message` inline with a `<details>` dropdown for the raw body. No client-side retry — if the matcher fix doesn't hold, the right answer is to find out and fix it, not mask it with retries.

When #83453 ships a fix, bump Next and we can delete the matcher exception. If the same stack reappears in prod logs after this matcher change, the bug isn't middleware-bound and we need a different approach.

### 5. `stopWhen: stepCountIs(8)`

Hard cap on tool-loop steps per turn. Set high enough for sweeping multi-file edits, low enough to bound cost on a runaway chain. Bump if you legitimately need >8 sequential tool calls — don't remove the cap.

### 6. Diagnostic watcher useEffect

The watcher in `AiChatPanel` that logs `pending tool parts` exists for debugging stuck-toast scenarios. It's idempotent (signature-deduplicated). Keep it — it's been the only way to confirm whether a hung UI is a tool-result delivery bug or a model-side hang.

### 7. Tool result shape isn't strictly typed end-to-end

`ToolResult` is `({ ok: true } & Record<string, unknown>) | { ok: false; reason: string }`. The toast renderer (`renderFileOpToast` in `AiChatPanel.tsx`) destructures it loosely. If you change a tool's success shape, update both the handler return type AND that renderer's destructuring — TS won't catch it.

## Env

- `ANTHROPIC_API_KEY` — required
- `ANTHROPIC_MODEL` — optional. Default `claude-sonnet-4-6`. Sonnet handles the multi-turn `askChoice → editFile` flow noticeably better than Haiku.
